# Telegram-чтение и доставка разделены

## Контекст

Чтение выбранных каналов требует клиентского API и пользовательской сессии, а уведомления должны отправляться ботом только владельцу. Альтернативой было использовать одну Telegram-идентичность и один транспорт для обоих направлений.

## Решение

Использовать два независимых компонента: MTProto reader с приватной пользовательской сессией для intake и Bot API transport для доставки digest в настроенный owner chat.

## Почему

У Bot API и пользовательского клиента разные полномочия и жизненные циклы credentials. Разделение не даёт исходящей доставке доступа к читательской сессии и позволяет отключать или переподключать один канал без подмены состояния другого.

## Последствия

Нужно отдельно настраивать, хранить и проверять bot token/chat и API ID/API hash/session. Отсутствие credentials одного компонента не должно выдавать успех и не обязано блокировать другой; эксплуатация получает два независимых статуса подключения.
